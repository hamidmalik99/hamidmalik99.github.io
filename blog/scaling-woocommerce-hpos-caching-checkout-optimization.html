WooCommerce HPOS and Data Caching: How to Scale Your Store

Hamid Ali AsadJanuary 2026 · 7 min read

The short answer

WooCommerce HPOS (High-Performance Order Storage) stores orders in dedicated tables instead of the WordPress posts tables, reducing database load. HPOS data caching, introduced in WooCommerce 9.6, caches raw order data in the HPOS data store and works best with a persistent object cache. Test both on staging before enabling them on a live store.

Key takeaways

  • HPOS moves orders into four dedicated tables built for e-commerce queries.
  • HPOS has been enabled by default for new installations since WooCommerce 8.2.
  • HPOS data caching, introduced in WooCommerce 9.6, caches raw order data and checks the cache before the database.
  • WooCommerce's large-store guide recommends testing locally and on staging, then switching with sync on and turning sync off gradually.
  • Integrations that read order data directly from the posts tables must be updated before switching.

If your WooCommerce store feels slower as orders pile up, the way order data is stored and cached is usually the first place to look. WooCommerce HPOS (High-Performance Order Storage) moves orders out of the general WordPress posts tables into tables built for e-commerce, and HPOS data caching adds a cache layer for that order data on top. This guide explains what each one does, how to switch a large store over safely, and how they fit with object caching and checkout improvements. It's written for store owners and the developers who look after their stores.

Why order storage slows WooCommerce down

Before HPOS, WooCommerce stored orders as a custom post type, in the same posts and postmeta tables WordPress uses for pages, blog posts and everything else. WooCommerce's own HPOS documentation says this "comes with performance issues". As a store grows, order lookups compete with every other kind of content in tables that weren't designed for order queries.

In practice, store owners tend to notice:

  • the Orders screen in the admin getting slower to load and search
  • reports and exports taking longer
  • more pressure on the database during busy periods, such as sales

What WooCommerce HPOS changes

HPOS stores orders in dedicated tables. The WooCommerce documentation lists four:

  1. wc_orders
  2. wc_order_addresses
  3. wc_order_operational_data
  4. wc_orders_meta

(Your database adds its own table prefix in front, usually wp_.)

The documentation says dedicated tables and indexes result in "fewer read/write operations and fewer busy tables", and that HPOS also makes targeted backups and restores easier and helps prevent race conditions.

From WooCommerce 8.2, released in October 2023, HPOS is enabled by default for new installations. Older stores may still be on the legacy posts storage. You can check under WooCommerce > Settings > Advanced > Features.

Check plugin compatibility first

The documentation explains that if a plugin isn't compatible with HPOS, the HPOS option is disabled in the Features screen, and a "View and manage" link lists the incompatible plugins. Update those plugins, replace them, or ask their developers about HPOS support before you switch.

HPOS data caching explained

HPOS data caching is a newer, separate setting. In its post on Order DataStore Caching, WooCommerce explains that from version 9.6 it introduced an option to cache raw order data within the HPOS data store layer.

The post explains the reasoning in short:

  • Before this, WooCommerce tried to cache whole order objects. Because of how those objects are serialised, only the order ID was really stored, so each order had to be rebuilt from the database, which meant extra queries.
  • With data caching on, the HPOS data stores cache the raw order data and order meta instead. When an order is requested, WooCommerce checks the cache first and only queries the database on a cache miss.
  • Order data and meta are stored in the orders_data and orders_meta cache groups, and order objects move to their own non-persistent order_objects group.

When the post was published, the feature was in alpha testing. To see the option, you added define( 'WOOCOMMERCE_ENABLE_ALPHA_FEATURE_TESTING', true ); to wp-config.php, then enabled it under WooCommerce > Settings > Advanced > Features. The post said WooCommerce planned to roll it out as a non-alpha feature in 9.7. Check the Features screen on your own version to see its current status.

Who needs to be careful

The same post says compatibility is only a concern if an extension:

  • bypasses WooCommerce's CRUD layer with direct database queries to change order data
  • extends the internal order data stores in a way that skips cache invalidation
  • relies on clearing the old orders cache group directly

If your store uses custom code or older plugins that write to orders directly, test HPOS data caching on staging first.

It works best with a persistent object cache

Data caching stores order data in WordPress's object cache. Without a persistent object cache, such as Redis or Memcached provided by your host, that cache only lasts for a single page load. With one, cached data is reused across requests. Ask your host whether a persistent object cache is available on your plan.

How to switch a large store to HPOS safely

WooCommerce has a guide to enabling HPOS on large stores. It sets out three phases.

Phase What to do WooCommerce's notes
1. Local test Enable HPOS on a development copy with all plugins and custom code Test checkout with every payment method, refunds, subscriptions and critical flows
2. Staging migration Copy the production database to staging and run wp wc hpos sync Time the migration; for WooCommerce's test store of 9 million orders it took about a week
3. Production Enable sync with posts authoritative, migrate, verify, then switch HPOS to authoritative Switching and reverting are hot migrations with no planned downtime

A few points from the guide are worth highlighting:

  • Verify the data. wp wc hpos verify_cot_data --verbose checks that orders migrated correctly.
  • Check outside systems. Data warehouses, shipping tracking and accounting systems that read the posts tables directly must be updated before you switch.
  • Turn sync off gradually. Keep compatibility mode on after switching, disable sync on read first, then disable sync fully once things are stable. On WooCommerce's own high-volume migration, they disabled sync on read after six hours and fully disabled sync after a week.
  • Pick a quiet time. If your store has a natural low-volume period, switch then, and plan to be online afterwards.

This is a summary. Read the full guide and test on staging before changing a live store.

Checkout and order flow

Faster order storage helps behind the scenes, but customers judge your store at checkout. Once HPOS is in place, common improvements include:

  • Remove fields you don't need. If you don't use a field, such as a second address line or company name for consumer orders, consider removing it.
  • Offer express payment options your payment provider supports, such as Apple Pay and Google Pay, for faster mobile checkout.
  • Load only what checkout needs. Plugins that add scripts to every page can slow checkout; limit them to the pages where they're used.
  • Connect fulfilment properly. Send orders to your shipping or warehouse system automatically, using its official WooCommerce integration or webhooks, rather than re-keying them.

For overall page speed, see my guide to Core Web Vitals on WordPress.

Common mistakes when moving to HPOS

  • Switching on a live store without testing. WooCommerce's guide starts with a local test and a staging migration for a reason.
  • Forgetting direct database integrations. Reports, feeds or accounting tools reading postmeta will quietly break or show stale data.
  • Turning off compatibility mode straight away. Keeping sync on for a while lets you revert to posts storage quickly if something goes wrong.
  • Enabling data caching without checking custom code. Code that writes to orders directly can leave cached data out of date.
  • Assuming caching fixes everything. Slow hosting, heavy themes and too many plugins still need attention.

Frequently asked questions

What is HPOS data caching in WooCommerce?

HPOS data caching is an option WooCommerce introduced in version 9.6. It caches raw order data and order meta inside the HPOS data store, so WooCommerce checks the cache before querying the database. It was released as an alpha feature, so check the Features screen on your version for its current status and test it on staging first.

Is HPOS enabled by default?

WooCommerce says HPOS has been enabled by default for new installations since version 8.2, released in October 2023. Stores created before then may still use the legacy WordPress posts storage. You can check and change the setting under WooCommerce, Settings, Advanced, Features, once your plugins are compatible.

Is it safe to move a live store to HPOS?

WooCommerce's guide for large stores recommends testing locally, migrating a copy on staging, then switching production with synchronisation on so you can revert quickly. It describes switching and reverting as hot migrations with no planned downtime. Test checkout, refunds and integrations at each stage, and keep a backup.

Do I need Redis for HPOS data caching?

HPOS data caching uses the WordPress object cache. Without a persistent object cache, such as Redis or Memcached from your host, cached data only lasts for one page load. With one, it can be reused across requests. Ask your host whether a persistent object cache is available on your plan.
